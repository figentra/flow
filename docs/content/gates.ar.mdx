لفلو نوعان من البوابات. **بوابات الحالة** تفحص المواصفة على الحالة التي تدّعيها، من مسوَّدة إلى منجزة. و**بوابة طلب
الدمج** تشغّل فحوص المستودع عند الرأس المدفوع وتنشر `fflow/gate` على الالتزام. ترفض البوابة العمل، لا الشخص: كل رفض
يسمّي ما ينقص، والملف والسطر، والإصلاح.

## بوابات الحالة

تسكن كل مواصفة مجلدها، `.agents/specs/<key>-<slug>/`، باسم قضيتها. تشغّل أوامر `flow-*` البوابة وهي تحرّك المواصفة،
ويشغّلها `fflow gate check <folder>` يدويًا.

| الحالة      | تتطلب                                                                                                                   |
| ----------- | ----------------------------------------------------------------------------------------------------------------------- |
| مسوَّدة     | المجلد `<key>-<slug>`، وسطرَ قضية، إن ضُبط، يسمّي مفتاح المجلد                                                          |
| موضَّحة     | توضيحات مكتملة، ومفتاح قضية حقيقي، ولا علامة `[NEEDS CLARIFICATION` باقية، وسطر تاريخ الحالة                            |
| مخطَّطة     | التصميم مكتوبًا (قسم التصميم في المواصفة لمواصفة `small`، و`plan.md` لـ`feature` و`big`)، والموافقات التي تحتاجها الفئة |
| مُمهَّمة    | `tasks.md` يجتاز `fflow gate tasks`: معرّفات المهام، والمتطلبات التي تغطيها كلٌّ منها، وتبعيات بلا دورات، وتغطية كاملة  |
| قيد التنفيذ | مهمة واحدة مؤشَّرة على الأقل، ولا يجد `fflow trace drift` تغييرًا خارج الأعضاء الذين تسمّيهم المواصفة                   |
| منجزة       | كل مهمة حية مؤشَّرة، وكل متطلب مغطًّى باختبار موسوم `@covers <key>:FR-001`                                              |

قد تتأخر الحالة عن عملها، ولا تسبقه أبدًا. ويضيف الإعداد المسبق `stackra` قواعد: استبيان الأثر عند موضَّحة، وفحص
الدستور وأوضاع النشر وخصائص الصحة عند مخطَّطة، ومسارات المهام عند مُمهَّمة.

تؤشّر فلو المهام، لا اليد. يؤشّر `fflow task done <key> <T###>` المهمة فقط حين يخرج أمر فحصها بالرمز 0 عند رأس
نظيف، ويسجّل ذلك. ويفشل `fflow check` على مهمة أُشّرت بلا دليل نجاح، وعلى موافقة تغيّرت وثائقها منذ أن أُعطيت.

## التتبّع

يُتتبَّع كل متطلب عبر العمل:

```text
requirement (FR) → task (T###, covers: FR-…) → test (@covers <key>:FR-…) → commit (Refs: <key>) → pull request
```

- `fflow trace trace <folder>` يطبع المصفوفة.
- `fflow trace drift` يسمّي تغييرًا خارج ما تقول المواصفة إنها تمسّه.
- `fflow trace ci` يجعل قواعد الإنجاز فحصًا في التكامل المستمر.

ويطبع `fflow parse <file>` ما تقرؤه فلو من ملف مواصفة أو خطة أو مهام، بصيغة JSON، حين تفاجئك قراءة بوابة.

## بوابة طلب الدمج

يفحص `fflow gate run` الرأس المدفوع للفرع، ولا يفحص أبدًا شيئًا غير ملتزَم به. يرفض شجرةً متسخة أو رأسًا ليس طرف
الفرع البعيد. ويشغّل `gate.check` من `flow.config.json` (افتراضيًا `pnpm verify`) عبر المشغّل المضبوط:

| المشغّل          | أين تعمل الفحوص                                                                    |
| ---------------- | ---------------------------------------------------------------------------------- |
| `github-actions` | سير عمل طلب الدمج نفسه، `fflow-gate.yml`، برمز للقراءة فقط وبلا سرّ                |
| `local`          | جهاز المستدعي                                                                      |
| `ssh`            | صندوق تسمّيه بمضيفه                                                                |
| `command`        | أمرك أنت، مثل أداة سطر أوامر لأسطول اختبار؛ و`--shards <n>` يوزّع الفحص بحسب الحزم |

النتيجة حالةُ التزام واحدة، `fflow/gate`، على ذلك الرأس بالضبط. تُنشر باسم تطبيق البوابة الذي يسمّيه الإعداد تحت
`apps.gate`، لا برمز شخصي أبدًا، وتكون `success` فقط حين يخرج الفحص بالرمز 0. ولا يثق `land` بمصدر سواها.

### حكم GitHub Actions

مع المشغّل `github-actions` لا يستطيع سير عمل طلب الدمج نشر الحالة: فهو لا يحمل إلا رمزًا للقراءة فقط. وحين يكتمل
تشغيله يحكم عليه `fflow-approve.yml` في الفرع الافتراضي. مهمة `verdict`:

1. ترفض ما لم يكن التشغيل سيرَ عمل بوابة هذا المستودع، لطلب دمج مفتوح من هذا المستودع؛
2. تقرأ خلاصة مهمة `check` من واجهة GitHub البرمجية، لا من مخرَج ولا من سجل أبدًا؛
3. تُبقي الحالة عند `pending` حتى يوافق المالك حين يغيّر طلب الدمج `.github/workflows/`، لأن طلب الدمج يتحكم في
   نسخته من سير عمل البوابة؛
4. تسكّ رمز تطبيق بوابة قصير العمر وتنشر `fflow/gate`.

تفكّ المهمة تشفير مفتاح التطبيق بنفسها، موقَّعةً بـGitHub OIDC (‏`secrets.oidc` في الإعداد)، فلا يحمل المستودع سرًّا
لها. يهيّئ المالك ذلك مرة واحدة: صلاحية `statuses: write` للتطبيق، ومنح فك التشفير لبيئة `fflow-approve` على الفرع
الافتراضي وحده، ومتغيّر المؤسسة `FIGENTRA_AUTOMATION` مضبوطًا على `on`.

## حين يكون main أحمر: بوابة خط الأساس

المستودع الذي يفشل main فيه بعض الفحوص أصلًا يمكنه أن يشترط فحص `Baseline` بدل البوابة الكاملة، فتبقى طلبات الدمج
الروتينية قادرة على الهبوط. أضف `baseline` إلى الإعداد فيصيّر `sync` الملف `fflow-baseline.yml`. على طلب الدمج يقارن
كل مهمة بنتائج main المسجَّلة ويمنع:

- مهمةً نجحت على main، أو مهمة جديدة، تفشل؛
- مهمةً شغّلها main وأسقطها طلب الدمج أو تخطّاها؛
- مهمةً مدرجة في `mustPass` (اختبارات العزل والتفويض والأسرار والرخص مثلًا) ليست خضراء؛
- مهامَّ فاشلة أكثر مما في main.

يفشل مغلقًا حين لا يوجد خط أساس. وتبقى فحوص الأمن مطلوبة بذاتها. `Baseline` بوابةُ دمج لا شهادةُ إصدار: ما زال
الإصدار يحتاج تشغيلًا أخضر بالكامل.
